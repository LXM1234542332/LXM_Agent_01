## 3.工具返回格式和代码假设不一致
```
工具协议对齐问题：工具调用成功，但返回结构和本地解析假设不一致，导致状态传递失效。

一个很典型的问题是，MCP / LangChain 工具的真实返回结构，和自己代码里假设的不一致。

我一开始默认工具返回的是 dict 或 JSON 字符串，但实际通过 langchain-mcp-adapters 返回的是 list[ContentBlock]，文本 JSON被包在 text 字段里。结果是 Triage 虽然调用成功了，但解析函数拿到的是空对象，后续 Planner 看到的都是降级默认值。

这个问题本质上不是“解析错了”，而是 Agent 框架层的抽象格式和业务层的数据消费格式没有对齐。这类问题在接LangChain、MCP、ToolNode 时很常见。

排查思路：
工具调用在日志里显示成功，但下游数据是空的。排查链路发现 _parse_tool_result
函数对返回值做了格式判断，但只有 tuple、str、dict 三个分支，没有 list 分支。

解决方式:
是去翻 langchain-mcp-adapters 的源码（tools.py 里的 _convert_call_tool_result），确认实际返回的是list[ContentBlock]，每个文本块是 {"type": "text", "text": "...json..."} 的结构。然后在解析函数里补上 list分支，遍历找第一个能 JSON 解析的 text 字段。

面试里可以这样说：
  “我遇到过一次工具调用成功但状态传递全失效的问题，最后发现不是模型问题，而是工具返回协议和本地解析逻辑不一致，导致
  Triage 拿到真实数据但下游看到的是空值。”
```


## 4.LLM 拿到太多工具后会“自作主张”
```
工具可见性问题：模型看到不该看到的工具后会自作主张，单靠 prompt 无法保证流程约束。
```

只要把工具暴露给模型，不代表模型一定按你的业务流程来用。

比如 set_scenario() 这个工具，本来只应该在最开始做场景初始化。但因为 Executor / Replanner 里 bind_tools(mcp_tools)时把所有工具都绑定给了模型，模型看到上下文里有 scenario_id，就会自作主张地先去调用set_scenario()，哪怕这个工具根本不在 Planner 生成的步骤里。

这个问题本质上说明：
Agent 的流程控制，不能只靠 prompt 约束，还要靠工具可见性控制。
也就是说，“模型能看到什么工具”本身就是流程设计的一部分。



解决方法：
排查思路是：Planner 生成的步骤列表里根本没有 set_scenario()，但 Executor
  执行日志里出现了它，而且执行完之后计划的第一步被跳过了。

解决方式：
在 Planner、Executor、Replanner 三处获取工具列表之后，统一过滤掉 set_scenario 和
  get_current_scenario，用一行列表推导式 [t for t in all_tools if t.name not in _EXCLUDED] 实现，让这两个工具在整个
  Plan-Execute-Replan 流程里对 LLM 不可见。


## 5. 计划、执行、总结这三层职责容易混淆
```
职责重复问题：Planner、Executor、摘要器的边界没切清时，很容易出现重复推理和重复调用。
```

在做 Plan-Execute-Replan 结构时，一个很容易踩的坑是：Planner、Executor、Replanner 的职责边界如果不清晰，模型会重复做同一件事。

你这里最明显的例子就是 Executor 阶段：
  - 第一次 LLM 调用负责选工具
  - ToolNode 负责执行工具
  - 后面又来了一次 LLM 调用做“结果总结”

问题在于，这个“结果总结”后面其实已经有 summarize_step 在做了，所以中间那次 LLM 调用是重复的；而且因为 prompt里还保留着“请执行以下步骤”，模型甚至可能再次触发工具调用。

这个问题很适合在面试里讲成：
  “我后来意识到 Agent 系统里最容易浪费 token 的不是模型能力不够，而是职责切分不清，导致同一个阶段重复推理。”


排查思路是：在 LangSmith 里发现同一步骤的工具被调用了两次，对着 Executor 代码逐行看，发现 ToolNode 执行完之后，原始
  messages（末尾还是"请执行步骤：xxx"）被整体传给了第二次 LLM 调用。

解决方式：
  删掉第二次 llm_with_tools.ainvoke，raw_result 直接从 ToolNode 返回的 ToolMessage 里取原始 JSON，后续的
  summarize_step 负责做文字总结，不需要再多一次 LLM 推理。同时把两次遍历 tool_messages["messages"]
  的逻辑合并成一次，顺便提取 tool_result_json 用于更新 ExactValuePool。



## 6. 摘要压缩和信息保真之间的权衡
上下文压缩问题：历史步骤必须压缩，但压缩过度会损失关键证据，影响 Replanner 决策质量。

  你这里还有一个很好的工程点：历史步骤不能全量塞给后续 LLM，所以要做摘要；但摘要一旦压缩过头，就会丢关键证据。

  你已经做了 summary 机制，这是对的。但后来又发现 Replanner 把 summary 截断成 400 字符，这会带来新的问题：
  - token 省了
  - 但 trace_id、时间戳、异常值这些关键证据可能丢了
  - Replanner 的判断质量反而下降

  这个问题的本质是：
  Agent 系统不是“能压缩就压缩”，而是要在上下文成本和关键信息保真之间做平衡。

  这是面试里很加分的话题，因为它能体现你对长链路 Agent 的上下文治理有实际经验。


排查思路是：
Replanner 做 continue 还是 respond 的判断时，发现它在格式化历史步骤时有一句
  summary[:400]，强行把每步摘要截断到 400 字符，而一个 trace_id 加时间戳加异常值凑在一起就超了。

解决方式: 很简单，就是把那行截断逻辑删掉，直接用完整的
  summary。核心判断是：摘要已经是压缩后的结果了，不应该再在使用时二次截断。 summarize_step
  阶段负责控制摘要长度，消费侧不应该再做截断。

## 7. 算法逻辑在真实场景数据上失效
```
算法落地问题：异常检测逻辑在静态上看没问题，但放到真实场景分布后会因为边界条件整体失效。
```

get_metrics_anomalies() 的问题也很适合拿出来讲，因为它不是语法 bug，而是算法在真实数据分布上失效。

原逻辑是 value > threshold，但实际 8 个场景的数据分布里，80 分位阈值刚好等于峰值本身，导致所有异常检测都失效。最后改成>= 才恢复正常。

这类问题面试里很好讲，因为它体现的是：
  “算法写得没错，但放进真实业务数据后边界条件把它击穿了。”

排查思路是：
get_metrics_anomalies() 返回的 anomalies 始终是空字典，直接写脚本把 8个场景的指标数据跑一遍，打印每个指标的值分布、80 分位阈值、最大值，以及 > threshold 和 >= threshold分别能检测到多少异常点。结果发现全部 8 个场景、所有指标，> threshold 的异常点数都是 0，原因是场景数据的构造规律是"正常期多、异常期少"，第 80百分位数恰好等于最大值本身，max > max 为 False。改成 >=之后全部恢复正常。这个案例说明在自己构造测试数据时要注意极值边界，> 和 >= 在百分位阈值场景下行为差异很大

## 8. Planner 阶段 LLM 自己"推理"改变了时间参数
```
问题描述：Triage 阶段提取的时间（开始、结束）都是正确的，但到了 Planner 阶段生成执行计划时，
end_time 被错误地改变了。

具体表现：
- 告警时间：2026-05-19T10:15:30Z
- Triage 计算的 analysis_start_time：2026-05-19T10:00:30Z ✅ 正确
- Triage 计算的 analysis_end_time：2026-05-19T10:20:00Z ✅ 正确
- Planner 生成计划中的 end_time：2026-05-19T10:30:00Z ❌ 错误（正好是 start + 30 minutes）

问题原因：
Planner 的 LLM 看到 start_time 后，自己推理出了一个"标准的 30 分钟查询窗口"，而不是直接使用
注入的 end_time 值。这是因为：
1. 提示词中对时间参数的约束不够强
2. Triage 上下文中时间参数的呈现不够显著，LLM 容易忽视 end_time

这个问题的本质：
Agent 系统中的 LLM 很容易基于部分信息进行推理并自作主张，仅靠提示词无法完全约束模型行为。
需要从"数据呈现"的角度强化约束——让关键参数更显著、更难被忽视。

排查思路：
1. 发现 Planner 生成的计划中 end_time 异常后，对比 Triage 阶段的输出
2. 注意到 end_time 恰好是 start_time + 30 minutes，这是 LLM 做推理的典型痕迹
3. 查看 _build_triage_context() 如何构建上下文，发现时间参数只是在 triage_context 中混在其他信息里
4. 检查 PLANNER_SYSTEM_PROMPT，发现对时间参数的使用没有明确约束

解决方式：
1. 在 PLANNER_SYSTEM_PROMPT 中添加"时间参数使用规则"部分，明确禁止：
   - ❌ 从 start_time 推导 end_time（如 start + 30min）
   - ❌ 修改或四舍五入时间戳
   - ❌ 使用"当前时间"而不是诊断锚点中的 end_time
   并提供正确做法的具体示例

2. 改进 _build_triage_context() 中时间参数的呈现，让 end_time 更显著：
   - 把时间参数从混合在其他信息中，改为单独提取并标记【重要】
   - 使用独立行显示 start_time 和 end_time，便于 LLM 直接复制
   - 格式改为：
     【重要】查询时间范围参数（直接用于工具调用，不要修改）：
       start_time = 2026-05-19T10:00:30Z
       end_time = 2026-05-19T10:20:00Z

修改的文件：
- app/agent/aiops/prompts.py：PLANNER_SYSTEM_PROMPT 中新增"时间参数使用规则"
- app/agent/aiops/planner.py：_build_triage_context() 函数中重构时间参数呈现

这个问题说明：
"在 Agent 系统中，约束 LLM 行为的不仅是提示词的文字，还包括数据的呈现方式。
关键参数要从背景中'突出'，使用清晰的格式和标记，让模型不太容易忽视或自作主张。"
```

## 9. Replanner 决策过程不透明，只能看到结果不知道原因
```
问题描述：Replanner 节点做出决策（continue/replan/respond），但日志中只显示最终的 action 结果，
看不到 LLM 是基于什么理由和依据做出的决策。这使得诊断流程的可追踪性和可解释性不足。

具体表现：
- 日志输出：
  Replanner 决策: continue
  (你只能看到这个，不知道为什么)

- 用户无法了解：
  ❓ 已有什么证据？
  ❓ 为什么做这个决策？
  ❓ 是否找到根本原因？
  ❓ 剩余步骤为什么还有价值？

问题影响：
1. 诊断过程的可追踪性差：无法理解整个诊断流程的决策链路
2. 调试困难：当 Replanner 做出意外决策时，无法快速定位原因
3. 用户体验差：无法获得诊断系统的完整推理过程
4. 性能评估困难：无法从决策推理看出 Agent 是否有足够的"思维能力"

这个问题的本质：
Agent 系统的决策节点需要"可解释性"。单纯输出决策结果（continue/respond）是"黑盒"行为，
用户看不到这个决策的推理过程，这会严重削弱 Agent 系统的可信度和可维护性。

排查思路：
1. 在日志中观察 Replanner 的输出，发现只有 action 字段，没有 reasoning 字段
2. 查看 Act 数据模型定义，发现只有 action 和 new_steps，缺少对决策理由的记录
3. 检查 REPLANNER_SYSTEM_PROMPT，发现对 LLM 的提示词中没有要求说明决策理由
4. 认识到 Agent 系统的决策应该像"思维过程"一样清晰可见

解决方式：
1. 扩展 Act 数据模型，添加 reasoning 字段：
   class Act(BaseModel):
       action: str              # continue/replan/respond
       reasoning: str           # ✨ 新增：决策的推理过程和依据
       new_steps: List[str]     # replan 时的新步骤

2. 修改 Replanner 执行逻辑，输出决策理由：
   reasoning = act.reasoning if isinstance(act, Act) else act.get("reasoning", "")
   logger.info(f"Replanner 决策: {action}")
   logger.info(f"决策推理: {reasoning}")  # ✨ 新增：输出推理过程

3. 增强 REPLANNER_SYSTEM_PROMPT，要求 LLM 详细阐述判断过程：
   - 添加"做决策前的检查清单"部分
   - 列出 4 个评估要点（证据充分性、剩余计划价值、执行步骤数、问题方向是否偏离）
   - 要求 LLM 逐条评估并在 reasoning 中说明判断
   - 提供 JSON 格式示例，明确说明 reasoning 字段的重要性

修改的文件：
- app/agent/aiops/replanner.py：
  * Act 类中添加 reasoning 字段
  * replanner() 函数中添加 reasoning 输出日志

- app/agent/aiops/prompts.py：
  * REPLANNER_SYSTEM_PROMPT 中新增"做决策前的检查清单"部分
  * 在 JSON 格式要求中明确说明 reasoning 字段必须详细

效果对比：

❌ 之前：
  Replanner 决策: continue
  (用户一头雾水，不知道为什么)

✅ 现在：
  Replanner 决策: continue
  决策推理: 
  已执行 3 步，收集到的证据包括：
  - 服务 payment-service 的错误日志显示连接池耗尽
  - 指标 db_connections 在 10:15 时从正常的 50 跃升到 200+
  - 部署事件显示 10:14 时有新版本发布
  
  根据以上证据，我已基本确认问题是新版本的连接泄漏。
  但 get_slow_traces 还未执行，可以用它来确认哪个服务调用链路出问题。
  因此继续执行下一步，而非立即结束。

这个问题说明：
"Agent 系统的'思维过程'必须可见。决策节点不仅要输出结果，还要输出推理过程。
这不仅提高了系统的可解释性和可信度，还能帮助用户和开发者理解 Agent 的'思维'质量。"

面试角度总结：
"我遇到过 Agent 系统中决策不透明的问题。一开始 Replanner 只输出 continue/respond，
用户完全看不到决策的推理过程。后来我为决策输出添加了 reasoning 字段，要求 LLM 详细说明
判断依据，这样不仅提高了系统的可解释性，还能评估 Agent 的思维质量。"
```

## 10. Planner 只输出计划列表，看不到为什么会得到这个计划的分析

  ❓ 为什么采用这个诊断策略？（需要什么证据）

1. 诊断流程不透明：用户看不到从"问题特征"到"诊断计划"的推理链路

这个问题的本质：
Agent 系统的中间过程必须"可观测"。不仅 Triage 和 Executor 要透明，Planner 的规划过程
也需要透明。从"数据→分析→计划"的完整链路都应该让用户可见，这样诊断流程才是真正意义上的
"可解释的 Agent"。

排查思路：
