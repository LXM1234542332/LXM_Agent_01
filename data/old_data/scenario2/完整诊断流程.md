# Scenario 2 - 完整诊断流程

## 场景描述
系统在2026-05-19 10:15时user-service部署了v2.3.1版本，随后出现连接泄漏告警，导致连接池耗尽，服务错误率上升。

---

## 一、Planner 阶段 - 诊断计划生成

**用户请求**：系统出现连接泄漏告警，请诊断问题原因

**Planner 生成的诊断计划**：
1. 调用 get_alerts() - 获取当前系统中的所有告警，了解问题范围
2. 调用 get_error_logs(limit=30) - 获取最近的错误日志，了解错误类型和受影响服务
3. 调用 get_metrics_anomalies(service=user-service) - 检查user-service的指标异常，特别是连接数和错误率
4. 调用 get_deployment_events(service=user-service) - 查看user-service的部署历史，找出问题触发点
5. 调用 get_slow_traces(limit=10) - 获取慢查询trace，分析性能问题
6. 调用 get_service_dependencies(service=user-service) - 查看user-service的依赖关系，了解问题影响范围

**计划步骤数**：6步

---

## 二、Executor 阶段 - 逐步执行诊断

### 步骤 1：获取当前告警

**执行内容**：调用 get_alerts()

**工具逻辑应用**：
- 从events.json中筛选event_type=="alert"的记录
- 按timestamp降序排序
- 返回最新的告警

**模拟执行结果**：
```
告警列表（按时间倒序）：
1. 时间：2026-05-19T10:18:00Z
   服务：order-service
   级别：warning
   消息：订单服务变慢

2. 时间：2026-05-19T10:15:30Z
   服务：user-service
   级别：critical
   消息：连接泄漏开始
```

**关键发现**：
- 发现2个告警，其中1个critical（user-service连接泄漏），1个warning（order-service变慢）
- 连接泄漏告警在10:15:30触发，order-service变慢告警在10:18触发
- 问题可能从user-service开始，然后影响到order-service

---

### 步骤 2：获取错误日志

**执行内容**：调用 get_error_logs(limit=30)

**工具逻辑应用**：
- 从logs.json中筛选level=="ERROR"的记录
- 按timestamp降序排序
- 返回最近的30条

**模拟执行结果**：
```
错误日志（共2条）：

1. 时间：2026-05-19T10:17:00Z
   服务：order-service
   消息：Database connection pool exhausted
   错误：Database connection pool exhausted
   Trace ID：trace_102

2. 时间：2026-05-19T10:16:00Z
   服务：user-service
   消息：Connection timeout: Failed to acquire connection from pool
   错误：Connection timeout: Failed to acquire connection from pool
   Trace ID：trace_101
```

**关键发现**：
- 两个错误都与数据库连接相关
- user-service在10:16:00出现连接超时错误
- order-service在10:17:00出现连接池耗尽错误
- 问题链条：user-service连接泄漏 → 连接池耗尽 → order-service无法获取连接

---

### 步骤 3：检查user-service的指标异常

**执行内容**：调用 get_metrics_anomalies(service=user-service)

**工具逻辑应用**：
- 从metrics.json中筛选service=="user-service"的记录
- 计算db_connections和error_rate的80th percentile作为阈值
- 找出超过阈值的异常值

**模拟执行结果**：
```
user-service 指标异常分析：

db_connections 异常：
- 正常值：36（10:00-10:14）
- 异常值：150（10:15-10:29）
- 异常时间：2026-05-19T10:15:00Z 开始
- 增长倍数：4.17倍
- 异常持续时间：14分钟

error_rate_percent 异常：
- 正常值：0.1%（10:00-10:14）
- 异常值：12%（10:15-10:29）
- 异常时间：2026-05-19T10:15:00Z 开始
- 增长倍数：120倍
- 异常持续时间：14分钟
```

**关键发现**：
- user-service的db_connections在10:15:00突然从36跳到150
- error_rate在同一时间从0.1%跳到12%
- 异常时间与部署时间（10:15）完全吻合
- 指标异常持续了14分钟

---

### 步骤 4：查看user-service的部署历史

**执行内容**：调用 get_deployment_events(service=user-service)

**工具逻辑应用**：
- 从events.json中筛选event_type=="deployment"且service=="user-service"的记录
- 按timestamp降序排序
- 返回最近的部署事件

**模拟执行结果**：
```
user-service 部署历史：

部署事件：
- 时间：2026-05-19T10:15:00Z
- 服务：user-service
- 版本：v2.3.1
- 状态：success
```

**关键发现**：
- user-service在10:15:00部署了v2.3.1版本
- 部署状态为success，但随后立即出现连接泄漏告警（10:15:30）
- 部署时间与指标异常时间完全吻合
- 问题根因很可能是v2.3.1版本引入的bug

---

### 步骤 5：获取慢查询trace

**执行内容**：调用 get_slow_traces(limit=10)

**工具逻辑应用**：
- 从traces.json中筛选total_duration_ms > 1000的trace（慢查询阈值）
- 按total_duration_ms降序排序
- 返回最近的10条

**模拟执行结果**：
```
慢查询 Trace（共2条）：

1. Trace ID：trace_102
   时间：2026-05-19T10:17:00Z
   总耗时：2500ms
   状态：error
   服务链：api-gateway → order-service
   错误：Database connection pool exhausted

2. Trace ID：trace_101
   时间：2026-05-19T10:16:00Z
   总耗时：3000ms
   状态：error
   服务链：api-gateway → user-service
   错误：Connection timeout: Failed to acquire connection from pool
```

**关键发现**：
- 两个慢查询都是错误trace，耗时都超过2.5秒
- trace_101显示user-service连接超时
- trace_102显示order-service连接池耗尽
- 问题影响了整个服务链
