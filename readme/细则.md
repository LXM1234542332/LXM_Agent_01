# 第一阶段实施细则

## 一、疑惑与方案总结

### 1. 数据生成的范围和精度

**疑惑**：数据量是否需要完全按照规划（300-400 条日志）？

**确定方案**：
- ✓ 生成真实和有意义的数据
- ✓ 减少数据量到 200-300 条日志（而不是 300-400）
- ✓ 减少指标到 100-150 条（而不是 150-200）
- ✓ 减少链路到 15-20 条（而不是 20-30）

**理由**：保证数据质量，同时减少工作量

---

### 2. 场景的时间范围

**疑惑**：每个场景应该有多长的时间范围？是否需要包含恢复状态？

**确定方案**：
- ✓ 统一使用 30 分钟时间窗口（10:00:00 - 10:30:00）
- ✓ **移除恢复状态**，只保留问题状态
- ✓ 时间分布：
  - 10:00-10:15：正常状态
  - 10:15-10:30：问题状态（持续进行中）

**理由**：运维 Agent 诊断的是当前存在的问题，不需要恢复状态

---

### 3. 场景加载的实现方式

**疑惑**：如何实现场景加载？是否可以不重启应用？

**确定方案**：
- ✓ 使用方法参数 + 环境变量组合
- ✓ **支持动态切换场景，不需要重启应用**
- ✓ 实现方式：
  ```python
  tools = DiagnosticDataTools()  # 初始化
  tools.switch_scenario('scenario2')  # 动态切换，无需重启
  ```

**理由**：便于测试和演示，提高效率

### 4. 工具的修改范围

**疑惑**：是否需要修改现有的 7 个工具？

**确定方案**：

- ✓ 如果修改会破坏兼容性，则保持不变
- ✓ 新增 3 个工具：get_service_dependencies()、get_trace_details()、get_slow_traces()

**理由**：在保证兼容性的前提下，优化功能

### 5. 数据的一致性

**疑惑**：数据一致性指的是什么？

**确定方案**：
- ✓ 数据一致性指不同数据文件之间的数据要相互对应和匹配

  - 时间戳在所有文件中一致

**理由**：确保 Agent 的诊断准确性

## 三、8 个场景的详细设计

### 场景1：级联故障（最复杂）

```
问题：payment-service 部署 Bug 导致级联故障
根因：payment-service 新版本存在 Bug，导致支付超时
表现：
  - payment-service 响应时间从 100ms → 5000ms
  - order-service 响应时间从 200ms → 5100ms
  - api-gateway 响应时间从 300ms → 5200ms
  - 错误率从 0.1% → 15%
时间范围：10:00-10:30
  - 10:00-10:15：正常状态
  - 10:15-10:30：问题状态
```

### 场景2：数据库连接泄漏（中等复杂）

```
问题：user-service 连接泄漏导致 DB 连接耗尽
根因：user-service 代码中连接未正确释放
表现：
  - DB 连接数从 36 → 150+（耗尽）
  - user-service 响应时间增加
  - order-service 响应时间增加（依赖 DB）
  - 错误率上升
时间范围：10:00-10:30
```

### 场景3：内存泄漏导致 GC 停顿（中等复杂）

```
问题：order-service 内存泄漏导致 GC 停顿
根因：order-service 代码中内存未正确释放
表现：
  - 内存使用率从 50% → 95%
  - GC 时间从 50ms → 500ms
  - 请求延迟增加
  - 错误率上升
时间范围：10:00-10:30
```

### 场景4：CPU 使用率过高（简单）

```
问题：search-service CPU 使用率过高
根因：搜索算法效率低下
表现：
  - CPU 使用率从 30% → 95%
  - 请求延迟增加
  - 错误率上升
时间范围：10:00-10:30
```

### 场景5：内存使用率过高（简单）

```
问题：cache-service 内存使用率过高
根因：缓存数据未正确清理
表现：
  - 内存使用率从 60% → 98%
  - 缓存命中率下降
  - 数据库查询增加
时间范围：10:00-10:30
```

### 场景6：磁盘空间不足（简单）

```
问题：database-service 磁盘空间不足
根因：日志文件未定期清理
表现：
  - 磁盘使用率从 70% → 98%
  - 数据库无法写入
  - 所有服务都无法正常工作
时间范围：10:00-10:30
```

### 场景7：队列堆积（中等复杂）

```
问题：notification-service 队列堆积
根因：通知处理速度慢
表现：
  - 队列深度从 100 → 8000
  - 通知延迟增加
  - 内存使用率增加
时间范围：10:00-10:30
```

### 场景8：外部依赖故障（复杂）

```
问题：database-service 宕机
根因：数据库进程崩溃
表现：
  - 所有依赖 DB 的服务都无法工作
  - 错误率 100%
  - 所有请求都超时
时间范围：10:00-10:30
```

## 四、数据结构规范

### logs.json 结构

```json
{
  "timestamp": "2026-05-19T10:15:00Z",
  "service": "api-gateway",
  "level": "INFO",
  "message": "Request processed successfully",
  "trace_id": "trace_12345",
  "span_id": "span_1",
  "parent_span_id": null,
  "duration_ms": 147,
  "status": "success",
  "error_message": null
}
```

**字段说明**：
- `trace_id`：链路追踪 ID，同一个请求的所有日志都有相同的 trace_id
- `span_id`：当前服务的 span ID
- `parent_span_id`：调用者的 span ID
- `status`：执行状态（success/error/timeout）
- `error_message`：错误信息（如果有）

### traces.json 结构

```json
{
  "trace_id": "trace_12345",
  "start_time": "2026-05-19T10:15:00Z",
  "end_time": "2026-05-19T10:15:00.150Z",
  "total_duration_ms": 150,
  "status": "success",
  "spans": [
    {
      "span_id": "span_1",
      "parent_span_id": null,
      "service": "api-gateway",
      "operation": "POST /order",
      "start_time": "2026-05-19T10:15:00Z",
      "end_time": "2026-05-19T10:15:00.150Z",
      "duration_ms": 150,
      "status": "success",
      "error_message": null
    }
  ]
}
```

### metrics.json 结构

```json
{
  "timestamp": "2026-05-19T10:15:00Z",
  "service": "user-service",
  "instance": "pod-1",
  "metric_name": "error_rate_percent",
  "value": 0.5,
  "unit": "%"
}
```

### scenarios.json 结构

```json
{
  "id": "scenario1",
  "name": "级联故障",
  "description": "payment-service 部署 Bug 导致级联故障",
  "root_cause": "payment-service 新版本存在 Bug，导致支付超时",
  "affected_services": ["payment-service", "order-service", "api-gateway"],
  "expected_diagnosis": "payment-service 部署后导致支付超时，级联影响其他服务",
  "difficulty": "hard",
  "key_metrics": ["request_latency_ms", "error_rate_percent"],
  "key_logs": ["payment timeout", "order timeout"],
  "time_range": ["2026-05-19T10:15:00Z", "2026-05-19T10:30:00Z"]
}
```

### 4. 数据生成的具体规则

#### 日志分配规则（200-300 条）

**按服务分配**：
- 根据场景涉及的服务数量分配
- 每个服务 40-60 条日志
- 其中，根因服务应该有更多的错误日志

**按日志级别分配**：
- INFO 日志：60-70%（正常操作日志）
- WARN 日志：10-15%（警告日志）
- ERROR 日志：15-25%（错误日志）

**按时间分布**：
- 10:00-10:15（正常状态）：主要是 INFO 日志
- 10:15-10:30（问题状态）：ERROR 和 WARN 日志增加

**具体例子**（级联故障场景）：
```
总计：250 条日志
- api-gateway：60 条（其中 ERROR 20 条）
- order-service：70 条（其中 ERROR 25 条）
- payment-service：80 条（其中 ERROR 40 条，因为是根因）
- database-service：40 条（其中 ERROR 10 条）
```

#### 指标分配规则（100-150 条）

**按指标类型分配**：
- 每个服务的每个指标类型有多个时间点的数据
- 时间间隔：1 分钟一条数据

**按服务分配**：
- 每个服务 15-20 条指标
- 每个指标类型 3-5 个时间点

**具体例子**（级联故障场景）：
```
总计：120 条指标
- api-gateway：20 条（error_rate、request_latency、db_connections）
- order-service：25 条（error_rate、request_latency、db_connections）
- payment-service：30 条（error_rate、request_latency、db_connections）
- database-service：20 条（db_connections、cpu_usage）
- 其他服务：25 条
```

#### 链路分配规则（15-20 条）

**按调用链路分配**：
- 每条链路代表一个完整的请求
- 链路中的 span 数量取决于服务的调用深度

**按时间分布**：
- 10:00-10:15：正常链路（成功、延迟低）
- 10:15-10:30：问题链路（超时、错误、延迟高）

**具体例子**（级联故障场景）：
```
总计：18 条链路
- 10:00-10:15：5 条正常链路
  - 每条链路：api-gateway → order-service → payment-service → database-service
  - 总延迟：150-200ms
- 10:15-10:30：13 条问题链路
  - 每条链路：api-gateway → order-service → payment-service（超时）
  - 总延迟：5000-6000ms
```

### 7. 其他实施细节

#### 关于 trace_id 的生成

**决策**：
- ✓ trace_id 格式：`trace_` + 5 位数字（如 `trace_12345`）

#### 关于服务实例的分配
