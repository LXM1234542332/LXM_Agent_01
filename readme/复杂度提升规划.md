### 3.2 告警类型设计

#### 3.2.1 8种告警类型

```
1. error_rate_percent（错误率）
   - 范围：0-100%
   - 阈值：5%
   - 说明：请求错误率

2. request_latency_ms（请求延迟）
   - 范围：0-10000ms
   - 阈值：1000ms
   - 说明：平均请求延迟

   - 范围：0-200

   - 范围：0-100%

   - 范围：0-100%

   - 说明：内存使用率

6. gc_time_ms（GC 时间）
   - 范围：0-5000ms
   - 阈值：500ms

7. queue_depth（队列深度）
   - 范围：0-10000

8. disk_usage_percent（磁盘使用率）
```

```json
  "service": "api-gateway",
```

**新增字段说明**：
- `trace_id`：链路追踪 ID，同一个请求的所有日志都有相同的 trace_id
- `span_id`：当前服务的 span ID
- `parent_span_id`：调用者的 span ID

- `error_message`：错误信息（如果有）

### 3.4 场景设计（8个独立场景）

#### 场景1：级联故障
```
问题：payment-service 部署 Bug 导致级联故障
根因：payment-service 新版本存在 Bug，导致支付超时
表现：
  - payment-service 响应时间从 100ms → 5000ms
  - order-service 响应时间从 200ms → 5100ms
  - api-gateway 响应时间从 300ms → 5200ms
  - 错误率从 0.1% → 15%
诊断步骤：
  1. 查看告警：发现 api-gateway 错误率高
  2. 查看链路：发现 payment-service 最慢
  3. 查看部署事件：发现 payment-service 最近部署
  4. 查看 payment-service 日志：发现支付超时
```

#### 场景2：数据库连接泄漏
```
问题：user-service 连接泄漏导致 DB 连接耗尽
根因：user-service 代码中连接未正确释放
表现：
  - DB 连接数从 36 → 150+（耗尽）
  - user-service 响应时间增加
  - order-service 响应时间增加（依赖 DB）
  - 错误率上升
诊断步骤：
  1. 查看告警：发现 DB 连接告警
  2. 查看指标：发现连接数持续上升
  3. 查看日志：发现连接超时错误
  4. 查看部署事件：发现 user-service 最近部署
```

#### 场景3：内存泄漏导致 GC 停顿
```
问题：order-service 内存泄漏导致 GC 停顿
根因：order-service 代码中内存未正确释放
表现：
  - 内存使用率从 50% → 95%
  - GC 时间从 50ms → 500ms
  - 请求延迟增加
  - 错误率上升
诊断步骤：
  1. 查看告警：发现 GC 时间告警
  2. 查看指标：发现内存使用率高
  3. 查看日志：发现 GC 停顿
  4. 查看部署事件：发现 order-service 最近部署
```

#### 场景4：CPU 使用率过高
```
问题：search-service CPU 使用率过高
根因：搜索算法效率低下
表现：
  - CPU 使用率从 30% → 95%
  - 请求延迟增加
  - 错误率上升
诊断步骤：
  1. 查看告警：发现 CPU 告警
  2. 查看指标：发现 search-service CPU 最高
  3. 查看日志：发现搜索请求处理时间长
```

#### 场景5：内存使用率过高
```
问题：cache-service 内存使用率过高
根因：缓存数据未正确清理
表现：
  - 内存使用率从 60% → 98%
  - 缓存命中率下降
  - 数据库查询增加
诊断步骤：
  1. 查看告警：发现内存告警
  2. 查看指标：发现 cache-service 内存最高
  3. 查看日志：发现缓存清理失败
```

#### 场景6：磁盘空间不足
```
问题：database-service 磁盘空间不足
根因：日志文件未定期清理
表现：
  - 磁盘使用率从 70% → 98%
  - 数据库无法写入
  - 所有服务都无法正常工作
诊断步骤：
  1. 查看告警：发现磁盘告警
  2. 查看指标：发现磁盘使用率高
  3. 查看日志：发现写入失败
```

#### 场景7：队列堆积
```
问题：notification-service 队列堆积
根因：通知处理速度慢
表现：
  - 队列深度从 100 → 8000
  - 通知延迟增加
  - 内存使用率增加
诊断步骤：
  1. 查看告警：发现队列深度告警
  2. 查看指标：发现队列堆积
  3. 查看日志：发现处理速度慢
```

#### 场景8：外部依赖故障（数据库宕机）
```
问题：database-service 宕机
根因：数据库进程崩溃
表现：
  - 所有依赖 DB 的服务都无法工作
  - 错误率 100%
  - 所有请求都超时
诊断步骤：
  1. 查看告警：发现多个服务错误率 100%
  2. 查看链路：发现所有链路都在 database-service 失败
  3. 查看日志：发现数据库连接失败
  4. 查看部署事件：发现数据库最近重启
```

### 3.5 MCP 工具设计（10个）

#### 现有工具（7个）

```
1. get_alerts()
   - 功能：获取所有告警事件
   - 参数：无
   - 返回：告警列表

2. get_error_logs(limit=20)
   - 功能：获取错误日志
   - 参数：limit（可选）
   - 返回：错误日志列表

3. get_logs_by_service(service, level=None, limit=20)
   - 功能：按服务名获取日志
   - 参数：service（必需），level（可选），limit（可选）
   - 返回：该服务的日志列表

4. get_logs_by_time_range(start_time, end_time, limit=50)
   - 功能：按时间范围获取日志
   - 参数：start_time（必需），end_time（必需），limit（可选）
   - 返回：时间范围内的日志列表

5. get_deployment_events(limit=10)
   - 功能：获取部署事件
   - 参数：limit（可选）
   - 返回：部署事件列表

6. get_metrics_anomalies()
   - 功能：获取指标异常
   - 参数：无
   - 返回：异常指标列表

7. get_metrics_by_service(service)
   - 功能：获取服务指标
   - 参数：service（必需）
   - 返回：该服务的指标列表
```

#### 新增工具（3个）

```
8. get_service_dependencies(service)
   - 功能：获取服务的依赖关系
   - 参数：service（必需）
   - 返回：该服务依赖的其他服务列表
   - 示例返回：["database-service", "cache-service"]

9. get_trace_details(trace_id)
   - 功能：获取链路的详细信息
   - 参数：trace_id（必需）
   - 返回：该链路的所有 span 信息
   - 示例返回：
     {
       "trace_id": "trace_12345",
       "total_duration_ms": 150,
       "spans": [...]
     }

10. get_slow_traces(threshold_ms, limit=10)
    - 功能：获取超过阈值的慢链路
    - 参数：threshold_ms（必需），limit（可选）
    - 返回：最近的 N 条慢链路
    - 示例返回：
      [
        {
          "trace_id": "trace_12345",
          "total_duration_ms": 5000,
          "spans": [...]
        }
      ]
```
