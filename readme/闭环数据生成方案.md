# 闭环数据生成方案总结

## 问题分析

之前的数据生成方案存在的问题：
- ❌ logs.json 和 traces.json 中的 trace_id 不对应
- ❌ 数据之间没有真正的因果关系
- ❌ Agent 无法通过链路追踪来诊断问题

## 新方案：闭环数据生成

### 核心思路

为每个场景手动设计完整的故障链条，确保：
1. **trace_id 对应** - logs.json 和 traces.json 中使用相同的 trace_id
2. **时间戳一致** - 所有数据使用相同的时间戳
3. **因果关系清晰** - events → logs → metrics → traces 都相互关联

### 实现方式

创建 `generate_closed_loop_data.py` 脚本，为每个场景定义：

```python
{
    "name": "场景名称",
    "root_cause_service": "根本原因服务",
    "timeline": [
        {"time": "...", "event": "deployment", "service": "...", "desc": "..."},
        {"time": "...", "event": "error_start", "service": "...", "desc": "..."},
        ...
    ],
    "traces": [
        {
            "trace_id": "trace_001",
            "start_time": "...",
            "services": ["service1", "service2", "service3"],
            "status": "error",
            "duration_ms": 5000,
            "error_msg": "..."
        },
        ...
    ],
    "metrics": {
        "error_rate_percent": {"normal": 0.1, "peak": 15},
        "request_latency_ms": {"normal": 100, "peak": 5000},
        ...
    }
}
```

### 数据生成流程

1. **生成 events.json**
   - 从 timeline 中提取部署事件和告警事件
   - 确保时间戳和服务名称对应

2. **生成 logs.json**
   - 正常状态日志（10:00-10:15）：使用 trace_normal_XXX
   - 问题状态日志（10:15-10:30）：使用 traces 中定义的 trace_id
   - 确保 trace_id 在 logs 和 traces 中对应

3. **生成 metrics.json**
   - 正常状态指标（10:00-10:15）：使用 metrics 中的 normal 值
   - 问题状态指标（10:15-10:30）：使用 metrics 中的 peak 值
   - 为每个受影响的服务生成指标

4. **生成 traces.json**
   - 正常链路：使用 trace_normal_XXX
   - 问题链路：使用 traces 中定义的 trace_id
   - 确保 trace_id 在 logs 和 traces 中对应

## 验证结果

### 数据一致性

```
logs 中的 trace_id:   ['trace_001', 'trace_002', 'trace_003', 'trace_normal_000', ...]
traces 中的 trace_id: ['trace_001', 'trace_002', 'trace_003', 'trace_normal_000', ...]
重叠的 trace_id:      ['trace_001', 'trace_002', 'trace_003', 'trace_normal_000', ...]
数据是否闭环:         YES ✓
```

### Agent 诊断能力

Agent 可以通过以下步骤诊断出问题原因：

1. **获取告警** → 发现 payment-service 有 critical 告警
2. **获取部署事件** → 发现 payment-service 最近部署了新版本
3. **获取错误日志** → 发现错误日志中有 "Payment service timeout"
4. **获取异常指标** → 发现 request_latency_ms 和 error_rate_percent 异常
5. **获取慢链路** → 发现有多条超过 1000ms 的链路
6. **获取链路详情** → 看到 payment-service 耗时最长
7. **获取服务依赖** → 确认 payment-service 是根本原因

**诊断结论：payment-service 部署 Bug 导致级联故障**
