# 根因准确率评估指标设计方案

## 一、总体设计

### 1.1 核心目标

评估运维诊断 Agent 的根因定位准确率，通过三个维度的评分来综合衡量诊断质量：
- **根因服务定位**：Agent 是否正确识别了故障源头服务
- **根因类型识别**：Agent 是否准确理解了故障的类型和特征
- **证据链完整性**：Agent 收集的证据是否能充分解释根因结论

### 1.2 最终评分公式

```
根因准确率 = 根因服务定位 × 0.40 + 根因类型识别 × 0.35 + 证据链完整性 × 0.25
```

权重分配的逻辑：
- **根因服务（0.40）**：最重要。如果连故障源头服务都找错了，后续的诊断就没有意义
- **根因类型（0.35）**：次重要。即使找对了服务，如果对故障类型的理解有偏差，也会误导运维决策
- **证据链（0.25）**：基础。证据链支撑了前两个维度的结论，但权重相对较低

---

## 二、三层级联评估逻辑

### 2.1 第一层：根因服务定位（精确匹配）

**评估方式**：精确字符串匹配

**评分规则**：
- 诊断结果的服务名 == 标准答案的服务名 → **1.0 分**
- 否则 → **0.0 分**

**短路逻辑**：
- 如果根因服务得分 < 1.0，则根因类型和证据链直接判为 0 分，评估结束
- 理由：服务都找错了，后续评估没有意义

**示例**：
- 标准答案：`payment-service`
- 诊断结果：`payment-service` → ✅ 1.0
- 诊断结果：`payment_service` → ❌ 0.0（不同的命名方式也算错）
- 诊断结果：`order-service` → ❌ 0.0

---

### 2.2 第二层：根因类型识别（LLM 语义打分）

**评估方式**：使用 LLM 对两段故障类型描述进行语义相似度评分，独立打分 2 次取平均，减少单次随机误差

**评分规则**：LLM 给出 0.0 ~ 1.0 之间的连续分数，精确到小数点后两位

**参考锚点**（端点固定，中间锚点使用非整数倍值，迫使 LLM 做真正的连续判断而非向整数倍靠拢）：
- **1.0**：语义完全等价，如"支付处理超时" 与 "timeout"
- **0.67**：同一类故障，但描述粒度或侧重点有差异，如"内存泄漏" 与 "内存异常占用"
- **0.28**：有一定关联但根因不同，如"超时" 与 "连接池耗尽"
- **0.0**：完全无关

**短路逻辑**：
- 如果根因类型得分 < 0.6，则证据链直接判为 0 分，评估结束
- 阈值 0.6 的含义：故障类型至少要"大体正确"才值得评估证据链
- 理由：如果对故障类型的理解有明显偏差（< 0.6），即使证据链再完整，也是在支撑一个错误的结论

**示例**：
- 标准答案：`新版本部署引入缺陷，支付处理超时`
- 诊断结果：`timeout` → LLM 打分 0.95 → ✅ ≥ 0.6，继续评估证据链
- 诊断结果：`支付超时` → LLM 打分 0.88 → ✅ ≥ 0.6，继续评估证据链
- 诊断结果：`内存泄漏` → LLM 打分 0.15 → ❌ < 0.6，证据链直接 0 分

---

### 2.3 第三层：证据链完整性（LLM 连续打分）

**评估方式**：使用 LLM 判断诊断报告能否解释清楚"根因服务发生了故障类型"，独立打分 2 次取平均，减少单次随机误差

**输入信息**：
- 根因服务（来自诊断结果/报告提取）
- 故障类型（来自诊断结果/报告提取）
- 诊断报告（Agent 输出的完整 Markdown 报告）

**评分问题**：
> 这份报告能否解释清楚「{根因服务} 发生了 {故障类型}」？

**评分规则**：LLM 给出 0.0 ~ 1.0 之间的连续分数，精确到小数点后两位

**参考锚点**（端点固定，中间锚点使用非整数倍值，迫使 LLM 做真正的连续判断而非向整数倍靠拢）：
- **1.0**：证据完整，完整解释了触发原因、故障现象、根因确认的完整链条
- **0.67**：主要证据齐全，但有少量细节缺失或表述不够清晰
- **0.28**：缺少关键证据，只能部分解释故障
- **0.0**：证据严重不足，无法解释该服务发生该故障


**示例**：

场景：payment-service 超时

标准答案根因：`payment-service 发生了支付处理超时`

诊断报告包含：
- ✅ payment-service 触发 critical 告警
- ✅ 9 条 Payment service timeout 日志
- ✅ 调用链末端是 payment-service
- ❌ 没有部署事件（无法解释触发原因）

LLM 评分：0.7（能解释"什么服务、出了什么问题"，但缺少"为什么出问题"）

## 三、评估流程

### 3.1 数据输入

**标准答案**（来自 `目标.json`）：
- `root_cause_service`：根因服务名
- `root_cause_type`：故障类型描述
- `key_evidence`：关键证据列表（用于参考，不直接参与评分）

**诊断报告**（来自 `运维agent报告.md`）：
- Agent 实际输出的完整诊断报告

### 3.2 评估步骤

**步骤 1**：从诊断报告中提取结构化信息
- 使用 LLM 从报告中提取：根因服务、根因类型
- 使用 tool use 强制返回结构化格式

**步骤 2**：评估根因服务定位
- 精确匹配对比
- 如果不匹配，直接结束，其他指标为 0

**步骤 3**：评估根因类型识别
- 使用 LLM 对两个故障类型描述进行语义打分
- 如果得分 < 0.6，证据链为 0，结束

**步骤 4**：评估证据链完整性
- 使用 LLM 判断报告能否解释清楚根因结论
- 获得 0.0 ~ 1.0 的连续分

**步骤 5**：计算最终评分
- 根据公式：0.40 × 服务 + 0.35 × 类型 + 0.25 × 证据链

### 3.3 短路机制的意义

三层级联评估中的短路机制确保：
- 如果根因服务错了，不浪费时间评估其他指标
- 如果根因类型偏差太大，不评估证据链（因为证据是在支撑错误的结论）
- 这样设计既提高了评估效率，也更准确地反映了诊断质量

## 四、关键设计决策

### 4.1 为什么根因服务用精确匹配？

- 服务名是固定的标识符，不存在"部分正确"的情况
- 即使只是大小写或命名方式不同，也代表诊断有问题
- 精确匹配能清晰地区分"对"和"错"

### 4.2 为什么根因类型用 LLM 打分而不是关键词匹配？

- 故障类型的表达方式多样，关键词匹配容易误判
- LLM 能理解语义等价性（如"超时" vs "timeout"）
- LLM 能识别细微差异（如"内存泄漏" vs "内存异常占用"）
- 连续分数比离散分数更能反映相似度的程度
- 不设定固定锚点值，让 LLM 自由给出精确到小数点后两位的分值，避免评分集中在少数离散值上导致的偏差

### 4.3 为什么证据链用 LLM 打分而不是逐条对比？

- 不依赖标准答案的证据列表，而是评估报告本身的说服力
- 关注的是"能否解释清楚根因结论"，而不是"有没有提到某类证据"
- 这样更接近真实的运维场景：运维人员看报告，能否理解故障原因
- 连续分数（精确到小数点后两位）比离散锚点值更能反映证据完整程度的细微差异

### 4.4 为什么证据链权重最低（0.25）？

- 根因服务和类型是"定位"问题，证据链是"支撑"问题
- 即使证据链完美，如果根因定位错了，整个诊断就是错的
- 权重分配反映了这个优先级：先对位置和类型，再看证据

### 4.5 为什么根因类型的阈值是 0.6？

- 0.6 代表"大体正确"的语义相似度
- 低于 0.6 意味着诊断的故障类型和标准答案有明显偏差
- 这种情况下，即使证据链再完整，也是在支撑一个错误的结论
- 0.6 这个阈值是在"容错性"和"准确性"之间的平衡

## 五、评估结果输出

### 5.1 单个场景的评分结果

```json
{
  "scenario_id": "scenario1",
  "scores": {
    "root_cause_service_accuracy": 1.0,
    "root_cause_type_accuracy": 0.88,
    "evidence_completeness": 0.7,
    "root_cause_accuracy": 0.82
  },
  "extracted": {
    "root_cause_service": "payment-service",
    "root_cause_type": "支付处理超时",
    "evidence_types": ["alert", "logs", "metrics", "traces"]
  },
  "ground_truth": {
    "root_cause_service": "payment-service",
    "root_cause_type": "新版本部署引入缺陷，支付处理超时"
  }
}
```

**说明**：
- `extracted.evidence_types` 记录了诊断过程中收集的证据类型，用于分析 Agent 的诊断行为
- 这个字段不直接参与评分，但对后续的 Agent 性能分析很有价值

### 5.2 全量评估的统计结果

- 成功评估的场景数
- 各指标的平均准确率
- 综合准确率的平均值

## 六、设计的优势

1. **清晰的层级结构**：三层评估逻辑清晰，每层的评分依据明确
2. **合理的短路机制**：避免在错误的基础上继续评估，提高效率
3. **语义理解能力**：使用 LLM 而不是规则，能处理表达方式的多样性
4. **权重分配合理**：反映了根因定位的优先级
5. **可解释性强**：每个分数都有明确的含义，便于分析诊断质量

## 七、应用场景

### 7.1 评估 Agent 性能

- 在多个测试场景上运行评估，获得综合准确率
- 对比不同版本 Agent 的性能改进

### 7.2 诊断质量分析

- 分析哪些场景的诊断质量较低
- 识别 Agent 的薄弱环节（是定位问题、类型识别问题，还是证据收集问题）

### 7.3 持续改进

- 根据评估结果调整 Agent 的诊断策略
- 优化证据收集的优先级和方式
