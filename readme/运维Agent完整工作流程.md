# 运维 Agent 完整工作流程详解

## 流程概览

```
告警产生
   ↓
[Planner] 制定诊断计划
   ↓
[Executor] 执行单个步骤（工具调用）
   ↓
[Replanner] 决策：继续/重新规划/结束
   ↓
[Report] 生成最终诊断报告
```

---

## 一、Planner 阶段（制定诊断计划）

### LLM 应该怎样思考

1. **分析用户输入**
   - 识别告警的关键信息：服务名、问题类型、严重程度
   - 确定诊断的目标：是发现问题根因还是评估影响

2. **规划诊断路径**
   - 第一步：总是 get_alerts() - 获取当前所有告警
   - 第二步：根据告警类型，选择收集数据的工具
   - 第三步及以后：逐层深入分析

### 调用什么工具

**Planner 不调用工具**，只是制定计划。调用的是 LLM 的 structured_output，让 LLM 返回结构化的计划列表。

### 返回数据格式

```json
{
  "steps": [
    "调用 get_alerts() - 获取当前系统中的所有告警",
    "调用 get_error_logs(limit=30) - 获取最近的错误日志",
    "调用 get_logs_by_service(service=根据告警确定的服务名, level=ERROR) - 深入分析受影响服务的错误日志",
    "调用 get_deployment_events(limit=10) - 获取最近的部署事件，看是否与告警相关",
    "调用 get_metrics_anomalies() - 获取异常指标"
  ]
}
```

### 规划原则

- **步骤数**：5-8 个（不要过少不要过多）
- **逻辑顺序**：先发现 → 再收集 → 再分析
- **参数化**：参数可以用中文描述，由 Executor 在运行时推断

---

## 二、Executor 阶段（执行诊断步骤）

### LLM 应该怎样思考

1. **理解当前步骤**
   - 解析步骤描述中的工具名和参数
   - 如果参数不完整（如"根据告警确定的服务名"），则根据已知信息推断

2. **选择合适的工具**
   - 步骤中可能已指定工具（如 get_alerts）
   - 或需要根据上文推断最合适的工具

3. **确定参数值**
   - 从模拟数据中推断合理的参数
   - 如果参数不确定，使用默认值

### 调用什么工具

通过 **bind_tools()** 绑定 MCP 工具，让 LLM 通过 Function Calling 自主决定调用哪个工具。

**可用的 MCP 工具：**

```
1. get_alerts()
   - 功能：获取所有告警事件
   - 参数：无
   - 返回数据示例：
     {
       "timestamp": "2026-05-19T10:25:00Z",
       "event_type": "alert",
       "service": "user-service",
       "severity": "warning",
       "message": "Database connection pool usage > 90%"
     }

2. get_error_logs(limit=20)
   - 功能：获取错误日志
   - 参数：limit（可选，默认 20）
   - 返回：最近的 N 条错误日志

3. get_logs_by_service(service, level=None, limit=20)
   - 功能：按服务名获取日志
   - 参数：service（必需），level（可选：ERROR/WARN/INFO），limit（可选）
   - 返回：特定服务的日志

4. get_logs_by_time_range(start_time, end_time, limit=50)
   - 功能：按时间范围获取日志
   - 参数：start_time（必需，格式：2026-05-19T10:20:00Z），end_time（必需），limit（可选）
   - 返回：时间范围内的日志

5. get_deployment_events(limit=10)
   - 功能：获取最近的部署事件
   - 参数：limit（可选，默认 10）
   - 返回：最近的 N 个部署事件

6. get_metrics_anomalies()
   - 功能：获取异常指标
   - 参数：无
   - 返回：检测到的指标异常

7. get_metrics_by_service(service)
   - 功能：获取特定服务的指标
   - 参数：service（必需）
   - 返回：该服务的各项指标（CPU、内存、网络等）
```

### 执行过程

```
1. 获取 MCP 工具列表
   ↓
2. LLM 通过 Function Calling 决定调用哪个工具
   ↓
3. ToolNode 执行工具调用
   ↓
4. 获取工具返回的原始数据
   ↓
5. LLM 整理结果，返回清晰的执行摘要
```

### 得到什么数据（真实示例）

**步骤 1：调用 get_alerts()**

```
返回数据：
- [CRITICAL] 高错误率告警：error_rate_percent = 15%（阈值 5%）
- [WARNING] 数据库连接池告警：db_connections = 95%（阈值 90%）
- [INFO] 部署完成事件：v2.3.1 -> v2.3.0（回滚）
```

**步骤 2：调用 get_error_logs(limit=30)**

```
返回数据：
- [ERROR] Connection timeout: Failed to connect to DB
- [ERROR] NullPointerException in UserService.getUser()
- [ERROR] OutOfMemory: Java heap space exhausted
- ...（更多错误日志）
```

**步骤 3：调用 get_logs_by_service(service=user-service, level=ERROR)**

```
返回数据：
- user-service pod-1: [ERROR] DB connection pool exhausted
- user-service pod-2: [ERROR] Query timeout after 30s
- user-service pod-3: [ERROR] Memory spike detected
- ...
```

### 分析过程（LLM 思维）

```
工具返回 → LLM 处理流程：

1. 识别关键信息
   - 哪些是直接信息（已明确提出的问题）
   - 哪些是隐含信息（需要推断的关联）

2. 建立因果关系
   - 告警（果）← 原因是什么？
   - 错误日志（因）→ 导致什么后果？

3. 提取关键发现
   - 受影响的服务：user-service
   - 问题类型：数据库连接耗尽
   - 触发时间：2026-05-19 10:25:00
   - 严重程度：CRITICAL

4. 生成执行摘要
   返回格式：
   **工具调用**：get_alerts()
   **执行结果**：
   - 发现 CRITICAL 告警：user-service 错误率 15%
   - 发现 WARNING 告警：user-service DB 连接池 95%
   - 发现关键信息：最近一次部署从 v2.3.1 回滚到 v2.3.0
```

## 三、Replanner 阶段（决策下一步）

### LLM 应该怎样思考

1. **评估已收集的数据**
   - 是否有足够的信息推断根因？
   - 是否已明确：受影响服务 + 问题类型 + 触发原因？

2. **做出决策**
   - 已有足够证据 → respond（生成报告）
   - 需要更多数据 → continue（执行下一步）
   - 原计划不适合 → replan（重新规划）

### 三种决策的选择标准

#### 决策 1：respond（结束，生成报告）- 最高优先级

**触发条件（满足任意一条即可）：**
- 已找到问题的根本原因，有足够的证据支撑
- 已执行步骤数 >= 5
- 剩余计划步骤为空

**LLM 思考过程：**
```
检查点 1：根因是否明确？
  ✓ 是 → respond
  ✗ 否 → 继续检查

检查点 2：已执行步骤 >= 5？
  ✓ 是 → respond（即使未找到根因也要结束）
  ✗ 否 → 继续检查

检查点 3：剩余计划为空？
  ✓ 是 → respond
  ✗ 否 → continue
```

**示例：**
```
已执行步骤：
1. get_alerts() → 发现错误率 15%、DB 连接耗尽
2. get_error_logs() → 发现连接超时错误
3. get_logs_by_service() → 发现所有 pod 都有连接问题
4. get_deployment_events() → 发现最近部署了 v2.3.1

LLM 结论：
根因已明确 → 新版本 v2.3.1 导致 DB 连接管理问题
证据充分 → 多个日志源都证实了连接问题
决策 → respond
```

#### 决策 2：continue（继续执行下一个步骤）- 中等优先级

**触发条件：**
- 尚未找到根本原因
- 剩余计划中的下一步确实能提供关键信息
- 已执行步骤数 < 5

**LLM 思考过程：**
```
问题 1：根因是否已明确？
  ✗ 否 → 继续检查

问题 2：已执行步骤 < 5？
  ✓ 是 → 继续检查

问题 3：剩余步骤能提供关键信息吗？
  ✓ 是 → continue
  ✗ 否 → respond（数据已足够，无需更多步骤）
```

**示例：**
```
已执行步骤：
1. get_alerts() → 发现告警存在，但原因不明

剩余计划中的下一步：get_error_logs()

LLM 结论：
问题：告警原因不明确
需要：更详细的错误日志来理解根因
决策 → continue（执行 get_error_logs）
```

#### 决策 3：replan（重新规划，替换剩余计划）- 最低优先级

**触发条件（必须同时满足）：**
- 原计划明显不适合当前情况（如发现了意外的问题方向）
- 已执行步骤数 < 3
- 新计划步骤数 <= 剩余步骤数

**LLM 思考过程：**
```
条件 1：原计划明显不适合当前情况？
  例如：原来计划分析"内存泄漏"，但实际发现"部署失败"
  ✓ 是 → 继续检查

条件 2：已执行步骤 < 3？
  ✓ 是 → 继续检查

条件 3：有新的更好的计划吗？
  ✓ 是 & 新计划步骤数 <= 剩余步骤数 → replan
  ✗ 否 → continue
```

**示例：**
```
原始请求：诊断 user-service 高 CPU 占用问题

已执行步骤：
1. get_alerts() → 发现不是 CPU 高占用，而是数据库连接耗尽！

原计划剩余步骤：
- 分析 CPU 使用情况
- 分析内存使用情况
- 分析线程数量

LLM 结论：
原计划基于错误的假设，应该重新规划
新计划：
- 分析数据库连接池
- 分析数据库查询性能
- 分析连接泄漏

决策 → replan（替换剩余计划）
```

### 继续计划还是修改计划的判断逻辑

```
已执行步骤结果：
   ↓
是否明确根因？
   ├─ 是 → respond（生成报告）
   └─ 否 → 数据足够吗？
         ├─ 是 → respond（无需更多数据）
         └─ 否 → 原计划仍适用吗？
               ├─ 是 → continue（执行下一步）
               └─ 否 → replan（重新规划）
```

## 四、报告生成阶段

### LLM 应该怎样思考

1. **综合所有执行结果**
   - 梳理 past_steps 中的所有步骤和结果
   - 提取关键信息点

2. **构建根因分析**
   - 表面现象是什么？
   - 根本原因是什么？
   - 两者之间的因果链条？

3. **给出建议**
   - 短期应对：立即可采取的行动
   - 长期改进：系统性的优化方向

### 报告结构

```markdown
# 🔍 系统诊断报告

**诊断时间**：2026-05-19 10:30:00
**诊断状态**：正常完成

## 一、告警概览
- 告警数量：2 个
- CRITICAL：高错误率 (15%)
- WARNING：数据库连接池 (95%)

## 二、根本原因分析

### 直接原因
- 新版本 v2.3.1 部署后错误率上升

### 根本原因
- 数据库连接池管理存在 Bug
- 新版本未正确释放连接

### 证据链
1. 部署事件：v2.3.1 上线
2. 错误日志：连接超时错误
3. 指标数据：连接数持续上升

## 三、受影响范围
- 服务：user-service（3 个 pod）
- 时间：2026-05-19 10:25:00 - 10:40:00（已回滚）
- 用户：约 500 个并发用户

## 四、建议
- 短期：已经自动回滚到 v2.3.0，故障已恢复
- 长期：需要修复新版本的连接池 Bug，增加单元测试覆盖
```

```markdown
## 二、根本原因分析

### 问题描述
user-service 在部署新版本 v2.3.1 后 10 分钟内出现高错误率和数据库连接耗尽，已自动回滚恢复。

### 直接原因
新版本 v2.3.1 存在数据库连接泄漏 Bug

### 根本原因
用户连接在某些代码路径中未被正确释放，导致：
1. 连接池逐渐耗尽（从 36 个 → 150+ 个）
2. 新请求无法获得连接，导致超时
3. 错误率急速上升（从 0.11% → 15%）

### 时间链条
```
10:15:00 ─ 部署 v2.3.1
    ↓
10:25:00 ─ 所有 pod 同时检测到连接泄漏
    ↓
10:25:00 ─ 告警触发（连接 > 90%，错误率 > 5%）
    ↓
10:25:30 ─ 运维人员点击"AI Ops"按钮
    ↓
10:25:55 ─ 自动诊断完成，根因已明确
    ↓
10:40:00 ─ 自动回滚到 v2.3.0
    ↓

## 六、关键设计点

### 1. Plan 的设计
- 灵活性：参数可以用中文描述，由 Executor 推断
- 可扩展性：支持 5-8 个步骤，不会过度诊断

### 2. Executor 的设计
- 自主性：通过 Function Calling 让 LLM 选择工具
- 容错性：工具调用失败时继续执行下一步

### 3. Replanner 的设计
- 终止机制：MAX_STEPS = 8，防止无限循环
- 决策优先级：respond > continue > replan
- 贪心策略：尽快结束，不追求完美

### 4. 数据流
- 单向传递：past_steps 只增不减
- 上下文积累：每一步的结果都被保留用于最后的报告
