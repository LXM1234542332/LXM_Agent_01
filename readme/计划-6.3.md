# AIOps 运维 Agent 改进方案 — 完整设计文档 (2026-06-03)

---

## 一、核心架构变化

### 旧架构（问题）
```
Planner（数据真空，靠经验规则生成计划）
  ↓
Executor（失忆，每步看不到前序结果）
  ↓
Replanner → 自然语言报告
```

### 新架构（目标）
```
Triage（强制调用 get_alerts + get_metrics_anomalies，建立故障画像）
  ↓ 写入 WorkingMemory（锚点参数）+ ExactValuePool（精确值）
Planner（有真实告警画像，生成有针对性的计划）
  ↓
Executor（每步注入 WorkingMemory + ExactValuePool + past_steps 摘要）
  ↓ 每步执行完：规则提取器更新 ExactValuePool + LLM 生成摘要
Replanner → 自然语言报告 + 结构化 RootCauseConclusion
```

---

## 二、核心设计决策

### 决策 1：两类参数分开处理

| 参数类型 | 定义 | 例子 | 解决方式 |
|---|---|---|---|
| 锚点参数 | 全程稳定，一旦确定不再变化 | 时间窗口、告警级别、场景ID | WorkingMemory 存储 |
| 动态推理参数 | 随诊断进展变化，需要 LLM 推断 | service、keyword、metric_name | past_steps 摘要注入 |

**不做"为每个工具参数预存好数据"** — 大多数参数是动态推理的结果，强行结构化反而有害。

---

### 决策 2：WorkingMemory（只存锚点参数，共 6 个字段）

```python
class WorkingMemory(TypedDict, total=False):
    # 时间锚点
    alert_first_trigger_time: str   # 最早告警触发时间（原始值，来自 get_alerts）
    analysis_start_time: str        # 查询窗口开始 = alert_first_trigger_time - 15min
    analysis_end_time: str          # 查询窗口结束 = 当前时间

    # 场景锚点
    scenario_id: str                # 当前诊断场景（来自系统初始化）

    # 告警概况
    alert_count: int                # 告警总数（来自 get_alerts）
    highest_severity: str           # 最高告警级别 critical/warning/info（来自 get_alerts）
```

**设计原则**：
- 字段少而精，只存真正全程稳定的值
- `analysis_start_time` 在 Triage 阶段计算好（告警时间前推 15 分钟），后续工具直接用，不重复计算
- 其他所有参数（service、metric_name、keyword、trace_id 等）不放进来

---

### 决策 3：ExactValuePool（精确值池，全局累积）

**作用**：解决"LLM 不能精确复现字符串"的问题（`payment-service` 被写成 `payment_service` 就失效）

```python
class ExactValuePool(TypedDict, total=False):
    known_services: List[str]       # 所有出现过的服务名（来自各工具结果）
    known_metric_names: List[str]   # 所有出现过的指标名
    known_trace_ids: List[str]      # 所有出现过的 trace_id
    known_event_types: List[str]    # 所有出现过的事件类型
    known_severities: List[str]     # 所有出现过的告警级别
    known_timestamps: List[str]     # 关键时间戳（保留最近 10 个）
```

**设计原则**：
- 全局累积，不限制轮数（服务名在第 1 步出现，第 6 步仍然有效）
- 只有 `known_timestamps` 限制数量（最近 10 个），避免 token 过长
- 值由**规则提取器**从 JSON 直接提取，不经过 LLM，保证 100% 精确
- 注入给 Executor 时，LLM 的任务是"从候选值中选择"而不是"凭记忆生成"

---

### 决策 4：规则提取器（每个工具单独配置）

**作用**：每次工具调用完成后，立即从返回的 JSON 里提取精确值，追加到 ExactValuePool。

**三种结构模式**：

| 模式 | 适用工具 | 提取方式 |
|---|---|---|
| `data` 数组型 | get_alerts、get_error_logs、get_events 等（大多数） | `[item["field"] for item in result["data"]]` |
| `anomalies` 字典型 | get_metrics_anomalies | `list(result["anomalies"].keys())` |
| `spans` 嵌套型 | get_trace_details | `[span["service"] for span in result["spans"]]` |

**覆盖范围（全部 15 个工具）**：

| 工具 | 提取字段 |
|---|---|
| get_alerts | service、severity、metric_name、trigger_time |
| get_error_logs | service、timestamp、trace_id |
| get_logs_by_service | trace_id、timestamp |
| get_logs_by_time_range | service、trace_id |
| get_logs_by_keyword | service、trace_id、timestamp |
| get_metrics_anomalies | metric_name、service |
| get_metrics_by_name | timestamp（异常值对应的） |
| get_metrics_by_time_range | metric_name、service、timestamp |
| get_deployment_events | service、timestamp、version |
| get_events | service、timestamp、event_type |
| get_events_by_type | service、timestamp |
| get_events_by_time_range | service、event_type、timestamp |
| get_slow_traces | trace_id、service |
| get_trace_details | trace_id、service |
| get_service_dependencies | service（upstream/downstream） |

---

### 决策 5：LLM 摘要器（分层去噪策略）

**作用**：每步工具调用完成后，立即调用轻量 LLM 生成摘要，供后续步骤注入上下文用。

**摘要原则**（不是按长度截断，而是按信息类型分层）：

```
① 异常/错误类记录    → 完整保留所有字段（服务名、时间、错误信息、ID）
② 关键数值          → 保留精确数字和单位
③ 正常/冗余记录     → 折叠为统计描述（"另有 N 条正常日志"）
④ 所有服务名、指标名、ID、时间戳 → 禁止改写，必须保留原文
```

**摘要长度**：由数据的异常密度决定，不人为限制。

---

### 决策 6：past_steps 存储结构变化

**旧结构**（二元组）：
```python
past_steps: List[Tuple[str, str]]
# (步骤描述, 原始结果)
```

**新结构**（StepRecord 三元组）：
```python
class StepRecord(TypedDict):
    step: str         # 步骤描述
    raw_result: str   # 工具原始返回（完整保留，供最终报告用）
    summary: str      # LLM 生成的分层去噪摘要（供 Executor 上下文注入用）
```

**注入策略**：
- Executor 执行时：注入所有步骤的 **summary**（摘要）
- 最终报告生成时：优先用 summary，必要时补充 raw_result

---

### 决策 7：Executor 执行时的完整上下文

每步执行前，LLM 看到的 messages：

```
[SystemMessage]
EXECUTOR_SYSTEM_PROMPT（更新：说明前序步骤和精确值池的含义）

[HumanMessage] 诊断锚点（WorkingMemory）
- 分析时间窗口：2026-06-02 14:15:00 ~ 2026-06-02 14:35:00
- 告警触发时间：2026-06-02 14:30:00
- 最高告警级别：critical
- 告警总数：2
- 场景ID：scenario1

[HumanMessage] 已知精确值（ExactValuePool，全局累积）
- 已知服务名（可直接用作 service 参数）：payment-service, order-service
- 已知指标名（可直接用作 metric_name 参数）：error_rate_percent, request_latency_ms
- 已知 trace_id：trace_001, trace_002
- 已知事件类型：deployment, alert
- 已知告警级别：critical, warning

[HumanMessage] 前序步骤摘要（全量步骤的 LLM 摘要）
步骤1：get_alerts()
[摘要内容：保留完整异常记录，折叠正常记录]

步骤2：get_metrics_anomalies()
[摘要内容]

[HumanMessage]
请执行以下步骤：xxx
```

## 三、新增 Triage 节点

**位置**：graph 入口，在 Planner 之前。

**职责**：
1. 强制调用 `get_alerts()`
2. 强制调用 `get_metrics_anomalies()`
3. 从结果中提取 WorkingMemory 的 6 个锚点参数
4. 调用规则提取器，初始化 ExactValuePool
5. 生成故障签名（fault_signature），注入 Planner 的 prompt

**故障签名格式**（注入给 Planner）：
```
当前故障画像：
- 告警数量：2个，最高级别：critical
- 受影响服务：payment-service, order-service
- 异常指标：error_rate_percent, request_latency_ms
- 告警触发时间：2026-06-02 14:30:00
- 分析时间窗口：2026-06-02 14:15:00 ~ 现在
```

## 五、PlanExecuteState 结构变化

```python
class PlanExecuteState(TypedDict):
    input: str                                             # 用户输入（不变）
    scenario_id: str                                       # 场景ID（不变）
    plan: List[str]                                        # 执行计划（不变）
    past_steps: Annotated[List[StepRecord], operator.add]  # 三元组（变化）
    working_memory: WorkingMemory                          # 新增：6个锚点参数
    exact_value_pool: ExactValuePool                       # 新增：全局精确值池
    response: str                                          # 最终响应（不变）
```
