# AIOps 诊断系统改进规划 (2026-06-02)

## 核心问题与改进框架

在根因准确率评估中发现了三个被报告质量掩盖的系统级缺陷。本文档从缺陷诊断、修复策略、架构优化到评估可靠性的完整改进方案。

---

## 第一优先级：修复两个核心缺陷（必做）

### 缺陷 1：Executor 失忆

**问题描述**
- 每次执行步骤时，LLM 拿不到前序步骤的结果
- 导致依赖型工具调用（如"根据告警确定的服务名"）只能靠猜
- 严重影响根因准确率

**修复方案**
将 `past_steps` 的摘要注入 executor 的 messages 中。这是改动最小、收益最大的一步。

**实现要点**
- 修改 executor.py，在每次调用前从 state 中提取已执行步骤
- 格式化为摘要文本（步骤序号、工具名、返回结果）
- 注入到 LLM prompt 的 system/user message 中

### 缺陷 2：Planner 在数据真空里生成计划

**问题描述**
- Planner 不调用任何工具，完全靠 prompt 里的经验规则生成计划
- 不同故障类型（CPU 高、部署缺陷、连接泄漏）生成的计划几乎是同一个模板
- 计划缺乏针对性

**修复方案**
在 Planner 之前加一个轻量的 **Triage 节点**：
1. 强制调用 `get_alerts()` 和 `get_metrics_anomalies()`
2. 获取真实的故障画像
3. 将故障画像注入 Planner 的 prompt

**实现要点**
- 新增 triage 阶段在 graph 中的定位
- 从 state 中提取告警和指标异常
- 生成结构化的故障签名（服务 + 异常类型 + 严重程度）

### 两个缺陷的关联性

这两个缺陷是一体的：
- 修了 Triage → Planner 有了真实数据
- 修了 Executor 失忆 → 后续步骤的参数才能用上 Triage 拿到的信息
- **两个一起做，才能形成完整的数据流闭环**

## 第二优先级：RAG 接到主流程（重要加分项）

### 现状分析

已有的资源：
- `aiops-docs/` 中的 5 个 runbook
- Milvus 向量库
- `retrieve_knowledge` 工具

**问题**：这些资源完全没有接入到诊断主流程

### 改进方案

**正确的接法：Triage 之后、Planner 之前**

1. 用 Triage 拿到的故障签名（例："payment-service 高延迟 + error_rate 飙升"）
2. 检索最匹配的 runbook
3. 将 runbook 的排查步骤注入 Planner 的 prompt

### 效果

使 Planner 生成的计划从 **"通用模板"** 变成 **"由真实告警 + 领域知识共同条件化的动态计划"**

### 面试表达建议

❌ "我加了 RAG"

✅ "我实现了 **Retrieval-Augmented Planning**——把运维 runbook 作为语义记忆，让诊断计划由真实告警和领域知识共同驱动"

（这个表述比"加个知识库问答"高级一个层次）

## 第三优先级：结构化根因输出（评估可靠性）

### 现有评估方案的问题

当前流程：
```
agent 输出自然语言报告 
  ↓ （有损抽取）
LLM 从报告里抽取结构化字段 
  ↓
和 目标.json 比对
```

**问题**：多了一道有损的抽取环节，导致评分不稳定

### 改进方案

让 Replanner 在生成自然语言报告的同时，**直接输出结构化的 RootCauseConclusion**

结构化字段对齐 `目标.json`：
- `root_cause_service`：根因服务
- `root_cause_type`：故障类型
- `key_evidence`：关键证据

### 评估流程优化

评估直接拿结构化字段比对，去掉抽取误差

```
Replanner 
  ↓
自然语言报告 + 结构化 RootCauseConclusion
  ↓ （直接比对，无抽取误差）
LangSmith 评估
```

### 对评分体系的影响

对"一总三分"评分体系的直接提升：
- 服务定位：40%
- 类型识别：35%
- 证据链：25%

在 LangSmith 上的评估结果更稳定、更可解释

## 第四优先级：记忆机制（架构亮点，重在设计）

### 三层记忆框架

这是教科书级的 agent memory 架构：

#### 1. 工作记忆（Working Memory）
- **定义**：单次诊断内的 `past_steps`
- **状态**：修 Executor 失忆后已经解决 ✓

#### 2. 语义记忆（Semantic Memory）
- **定义**：runbook 知识库
- **状态**：接 RAG 后已经解决 ✓

#### 3. 情景记忆（Episodic Memory）
- **定义**：历史已解决工单的向量化存储
- **检索**：下次遇到相似告警时检索"最相似的历史 case"
- **注入**：注入到 Planner prompt

### 情景记忆实现思路

**存什么**
- 告警签名 → 根因 + 处置动作
- 故障特征向量 + 解决方案

**怎么检索**
- 语义相似度匹配

**注入到哪里**
- Planner prompt（作为历史案例参考）

**为什么有价值**
- 让 agent 能从历史经验中学习
- 而不是每次从零开始

### 实现细节

**当前状态**：
- `aiops_service.py` 编译图时没传 `checkpointer`
- 但 `execute()` 里传了 `thread_id`
- 导致 session 状态目前是不持久的

**需要补充**：
- 补上 `MemorySaver`（参考 `rag_agent_service.py` 里的用法）
- 实现持久化存储

## 第五优先级：主动暴露并发 Bug（面试加分，不用修）

### Bug 描述

`diagnostic_server.py` 里的场景切换修改全局可变实例 `switch_scenario`：
- 两个并发会话诊断不同 scenario 会互相覆盖
- 存在并发安全问题

### 处理建议

**不建议修的原因**
- 修了反而让代码复杂
- 演示场景用不到并发

**面试表达策略**

主动提出这个问题，说：

> "我发现了这个并发安全问题。正确做法是把 `scenario_id` 作为工具参数传入或每会话隔离。但当前演示场景是单会话串行的，所以暂时可接受这个权衡。"

**价值**

这种表达方式比实现 10 个功能都有价值：
- ✓ 发现问题的能力
- ✓ 知道正确解法
- ✓ 有意识地做了取舍决策
- ✓ 能清晰表述权衡

## 改进后的架构对比

### 旧架构（数据流割裂）

```
Planner(数据真空)
  ↓
Executor(失忆)
  ↓
Replanner
  ↓
自然语言报告
```

### 新架构（数据流闭环）

```
Triage(get_alerts + get_metrics_anomalies)
  ↓ [故障画像]
RAG检索(runbook语义匹配)
  ↓ [领域知识]
Planner(数据驱动 + 知识增强)
  ↓ [动态计划]
Executor(注入past_steps，参数有据可依)
  ↓
Replanner
  ↓ [自然语言报告 + 结构化RootCauseConclusion]
LangSmith评估(直接比对结构化字段，无抽取误差)
```
