# 真实运维环境数据全景分析

## 一、日志数据

日志是排查问题的第一手资料，但真实环境中日志远不止"应用日志"一种。

### 1. 应用日志
- 业务逻辑日志（INFO/WARN/ERROR）
- 异常堆栈（Stack Trace）
- 请求/响应日志（包含 trace_id、耗时、状态码）
- 慢操作日志（慢 SQL、慢接口）

### 2. 系统日志
- 内核日志（`/var/log/kern.log`）：OOM Killer 触发、硬件错误
- 系统日志（`/var/log/syslog`）：进程崩溃、资源耗尽
- 安全日志（`/var/log/auth.log`）：异常登录、权限变更

### 3. 中间件日志
- Nginx/网关日志：4xx/5xx 错误率、请求量、上游超时
- 数据库日志：慢查询、死锁、连接数超限
- 消息队列日志：消息堆积、消费延迟、连接断开
- Redis 日志：内存淘汰、连接数、慢命令

### 4. 容器/编排日志
- Pod 事件日志（OOMKilled、CrashLoopBackOff、Evicted）
- 节点日志（Node NotReady、磁盘压力）
- 调度日志（Pod 无法调度的原因）

**结论**：仅靠应用日志远远不够，很多问题（如 OOM、网络抖动、数据库死锁）只能从系统日志或中间件日志中发现。

## 二、监控指标（Metrics）

监控指标是判断"是否有问题"和"问题严重程度"的核心依据。

### 1. 基础资源指标
- CPU：使用率、负载（Load Average）、上下文切换次数
- 内存：使用率、可用内存、Swap 使用量、Page Fault 次数
- 磁盘：使用率、IO 读写速率、IO 等待时间（iowait）、IOPS
- 网络：带宽使用率、丢包率、TCP 连接数、重传率

### 2. 应用层指标
- QPS（每秒请求数）
- 响应时间（P50/P95/P99）
- 错误率（4xx/5xx 比例）
- 并发连接数

### 3. JVM 指标（Java 应用）
- 堆内存使用率
- GC 频率和耗时（Full GC 是重点）
- 线程数、死锁线程数
- 类加载数量

### 4. 数据库指标
- 连接池使用率
- 慢查询数量
- 锁等待时间
- QPS/TPS
- 主从延迟（复制延迟）

### 5. 中间件指标
- 消息队列：消息堆积量、消费速率、生产速率
- Redis：命中率、内存使用率、连接数、慢命令数
- Nginx：活跃连接数、请求处理时间

**结论**：仅靠 CPU 和内存两个指标远远不够，很多问题（如数据库慢查询、GC 压力、消息堆积）需要专项指标才能发现。

## 三、链路追踪（Tracing）

这是日志和监控都无法替代的数据类型，在微服务架构中尤为重要。

### 核心价值
- 一个请求经过多个服务，能看到每个服务的耗时
- 能定位是哪个服务、哪个接口、哪个数据库操作导致了慢响应
- 能看到服务间的调用关系和依赖链

### 包含的信息
- Trace ID（全链路唯一标识）
- Span（每个服务节点的耗时）
- 服务调用关系图
- 每个节点的状态（成功/失败）

### 典型场景
- 用户反馈某个接口慢 → 通过 Trace 定位是数据库查询慢还是下游服务慢
- 某个服务报错 → 通过 Trace 找到是哪个上游服务触发的

**结论**：没有链路追踪，微服务架构下的性能问题几乎无法精确定位。

## 四、事件数据（Events）

事件是"某个时刻发生了什么"的记录，与监控指标的"持续状态"互补。

### 1. 变更事件
- 代码发布记录（什么时间、谁发布了什么版本）
- 配置变更记录（修改了哪些配置项）
- 数据库 DDL 变更（加了索引、改了表结构）
- 基础设施变更（扩容、缩容、网络变更）

### 2. 告警事件
- 告警触发时间、恢复时间
- 告警级别（critical/warning）
- 历史告警记录（同一问题是否反复出现）

### 3. 系统事件
- 服务重启记录
- 节点宕机/恢复记录
- 自动扩缩容记录

### 核心价值
- 排查问题时，第一件事是看"出问题前有没有变更"
- 80% 的线上故障都与变更有关
- 没有变更记录，排查时间会大幅增加

**结论**：变更记录是排查问题的关键上下文，缺少它就像"断案没有时间线"。

---

## 五、拓扑与依赖关系

### 服务依赖图
- 当前服务依赖哪些下游服务
- 哪些上游服务依赖当前服务
- 依赖的数据库、缓存、消息队列

### 核心价值
- 某个服务出问题，能快速判断影响范围
- 下游服务超时，能快速找到根因服务
- 避免"头痛医头"，找到真正的根因

---

## 六、用户/业务数据

### 核心指标
- 用户投诉量（用户感知到的问题）
- 业务成功率（订单成功率、支付成功率）
- 活跃用户数变化

### 核心价值
- 技术指标正常，但用户投诉增加 → 说明有业务逻辑问题
- 技术指标异常，但业务无影响 → 可以降低处理优先级

## 真实排查问题的完整流程

```
告警触发
  ↓
1. 看告警详情（什么服务、什么指标、触发时间）
  ↓
2. 看变更记录（出问题前有没有发布/配置变更）
  ↓
3. 看监控大盘（CPU/内存/网络/数据库等全局指标）
  ↓
4. 看链路追踪（定位是哪个节点慢/报错）
  ↓
5. 看日志（找具体的错误信息和堆栈）
  ↓
6. 看依赖关系（判断是自身问题还是下游问题）
  ↓
7. 得出结论，执行处理方案
  ↓
8. 验证恢复，写故障复盘
```

## 对项目的建议

基于以上分析，项目中最值得补充的数据类型（按优先级）：

### P0（必须有，否则诊断无法进行）

| 工具名 | 用途 |
|--------|------|
| `get_active_alerts` | 告警列表，这是诊断的起点 |
| `query_error_logs` | 有意义的错误日志，包含 ERROR 信息、堆栈、trace_id |

### P1（有了会大幅提升诊断质量）

| 工具名 | 用途 |
|--------|------|
| `get_recent_changes` | 变更记录，模拟最近的发布/配置变更 |
| `query_trace` | 链路追踪，模拟慢请求的调用链 |
| `get_service_status` | 服务状态，查询服务是否正常运行 |

### P2（锦上添花）

| 工具名 | 用途 |
|--------|------|
| `query_db_metrics` | 数据库指标，模拟慢查询、连接数 |
| `query_network_metrics` | 网络指标，带宽、丢包率、TCP 连接数 |
| `query_business_metrics` | 业务指标，模拟成功率、QPS、响应时间 |

## 结论

仅靠日志和监控数据**不足以**排查所有问题。真实运维中，完整的排查需要：

1. **告警** → 知道出了什么问题
2. **变更记录** → 知道出问题前发生了什么
3. **监控指标** → 知道问题的严重程度和趋势
4. **链路追踪** → 知道问题出在哪个服务/节点
5. **日志** → 知道具体的错误原因
6. **依赖关系** → 知道影响范围

这六类数据缺一不可，共同构成了完整的运维排查体系。
